# Schedule reminder delivery: per-due-occurrence turn injection, not per-turn injection

## Where this note lives and why

`.agents/notes/` is a closed RFC taxonomy: `scripts/agent-note-tree.ts:12,19` fixes `AGENT_NOTE_LIFECYCLES = ['proposed', 'implemented', 'rejected']` and `AGENT_NOTE_CLASSES`, and rejects unknown folders (`scripts/agent-note-tree.ts:53-54`). A one-off verification answer is not an RFC, and `docs/` is gate-managed (`pnpm run doc-sync`, `scripts/run-gates.ts:754-755`). This ungated root `research/` directory holds the answer without perturbing either tree.

## Answer in one paragraph

No. `packages/schedule/schedule` never injects anything on every turn and never injects into a turn that is being prepared. It delivers a model-visible user message only when a reminder's durable `scheduledAt` instant is due, only after the agent reaches a true idle boundary, and each delivery **starts** a new turn via `followup()` rather than joining an existing request (`packages/schedule/schedule/src/runtime.ts:267-273`). At `agent_start` (runtime mount) it runs one preflight that dispatches only already-overdue reminders, exactly once (`packages/schedule/schedule/src/runtime.ts:98-100`; test `jsonl-restart.spec.ts:98`). Due-time-driven delivery exists because reminders mature at arbitrary wall-clock instants while the session is live, and agent_start-only injection would miss all of them; tool copy states the boundary explicitly: "Delivery is session-local: the reminder runs on time only while this session is live" (`packages/schedule/schedule/src/tools.ts:153-154`). The per-step "Time sampled while preparing turn N, step M" block the maintainer observes is a different plugin, `packages/context/time-context`, which appends a snapshot reading at every eligible model-request preparation through an `agent/pre-step` listener (`packages/context/time-context/src/index.ts:181-221`, text at `:105`). The Schedule overlay mounts both plugins together, which is why the two mechanisms appear intertwined (`apps/cli/config/examples/schedule/cordis.yml:4-8`).

## 1. What actually happens: the schedule delivery mechanism

**Delivery triggers (all coalesced into one serial drive loop).** `ScheduleRuntime.requestDrive()` is the single entry (`packages/schedule/schedule/src/runtime.ts:103-128`); triggers are:

- runtime mount: `start()` calls `requestDrive()` (`runtime.ts:97-100`), installed from the plugin's `agent/created` listener for root agents only (`packages/schedule/schedule/src/index.ts:52-54,63`);
- a `setTimeout` timer armed at the next due target, segmented at `MAX_TIMER_DELAY_MS`; every wake re-samples the wall clock (`runtime.ts:178-184`, `:22`);
- an `agent/status === 'idle'` listener (`index.ts:57-62`);
- the schedule tool commit callback `onDurableChange` → `requestDrive()` after any successful management preflight (`index.ts:56`; `packages/schedule/schedule/src/tools.ts:297-315`).

**The drive step claims the idle phase.** `driveOnce()` first flushes persistence (`runtime.ts:233`), folds the durable `schedule/change` stream (`runtime.ts:205-216,242`), and decides: one due one-shot, one complete fixed-rate batch, or wait+re-arm (`runtime.ts:35-69`). A dispatch only proceeds inside `agent.runMaintenance(...)` (`runtime.ts:254`), which throws synchronously unless the agent's phase is `idle` (`packages/core/agent-loop/src/agent.ts:157-158`). On that synchronous rejection the runtime does not retry on a timer; it parks on `whenIdle()` and re-drives at the idle boundary (`runtime.ts:305-309`, `:187-203`; pinned by `runtime.spec.ts:216` "keeps an overdue record active until whenIdle permits maintenance").

**What the model receives.** Inside maintenance the runtime renders the fixed framing (`renderReminderFraming`, `packages/schedule/schedule/src/domain.ts:806-814`, or `renderEveryReminderBatchFraming`, `domain.ts:821-834`), builds a user message with `source: { kind: 'plugin', plugin: 'schedule' }`, and calls `agent.followup(message)` (`runtime.ts:266-273`). Only after the synchronous enqueue returns does it append the durable `schedule/change` `{ operation: 'dispatch' }` record(s) (`runtime.ts:280-296`), release maintenance, and flush again (`runtime.ts:310-319`). Ordering test: `runtime.spec.ts:240` ("orders preflight, maintenance, framing followup, dispatch, release, and barrier").

**`followup` opens the next turn; it never mutates a request being built.** `followup(input)` is `send(input, 'next-turn', true)` (`agent.ts:137-139`), contrasting `steer` = `send(input, 'next-step', true)` (`agent.ts:141-143`) and `inject` = `send(input, 'next-step', false)` (`agent.ts:145-147`). A `next-turn` message is durably recorded as an `agent/inbox/spliced` event at enqueue time (`packages/core/agent-loop/src/inbox.ts:169-176,238`), and is claimed as the opening user message of a new turn: `turn()` targets `'next-turn'` on its first pre-step (`agent.ts:284,289`) and `claim()` consumes next-step input plus one queued turn message (`inbox.ts:111-116`); the loop logs claimed messages as `user/message` events (`agent.ts:373-377`). A wake while busy is latched and replayed at convergence (`agent.ts:187-208`). Reminders therefore never interrupt a running turn — matching the README: "Due reminders appear as ordinary follow-up messages after the conversation becomes idle; the agent never interrupts a running turn" (`packages/schedule/schedule/README.md:56`).

**Correcting the "every turn" premise.** Schedule injects per **due occurrence**, not per turn. With nothing due, `dueDecision` returns `wait` and the drive only arms a timer (`runtime.ts:64-68,247-250`); an idle transition with no due record produces no message. A delivered one-shot is terminal (`domain.ts:557-562`); a fixed-rate (`every`) record advances to its next creation-aligned target and fires again at that later wall-clock instant (`domain.ts:520-552,557-568`). So a short `every_seconds` reminder does produce a new user message per interval — which can look like per-turn injection — but the cadence is the interval clock, not the turn loop, and it is batched: one message per interval containing all due every-reminders, one latest occurrence per record (`runtime.ts:49-62`; `tools.ts:151-152` "batch one latest occurrence per overdue rule"; test `runtime.spec.ts:280`; design note `.agents/notes/implemented/feature/2026-08-05-durable-web-schedule.md:23,49`).

**At agent_start.** `start()` runs the same preflight, and `dueDecision` admits only records whose `scheduledAt <= now` (`runtime.ts:43-52`) — i.e. exactly the already-overdue reminders, once. `jsonl-restart.spec.ts:98` ("resumes one overdue reminder exactly once across fresh runtime mounts") proves a restart dispatches the overdue reminder and a further restart re-dispatches nothing (`:145-150`).

## 2. Why due-time delivery instead of agent_start-only injection

- **Reminders mature mid-session.** A reminder created at turn 10 for +30 minutes becomes due while the session is live and idle-running; only a wall-clock trigger delivers it on time. The scope is explicitly session-local: "the reminder runs on time only while this session is live and otherwise becomes overdue until the session is resumed" (`tools.ts:153-154`; README `:214`; design note `:24` — a cold session keeps the record but runs no timer).
- **agent_start already owns the overdue case.** The mount preflight is the resume path; it dispatches what matured while the session was away, once (`runtime.ts:97-100`; `jsonl-restart.spec.ts:98`). Delivery-while-live and resume-on-mount are two triggers over one decision function, not competing mechanisms.
- **Delivery must wait for a safe turn boundary.** The loop is a single-threaded turn/step state machine (`agent.ts:41-49`); `runMaintenance` is the public idle-phase claim (`agent.ts:157-177`), and `followup` is the public next-turn queue (`agent.ts:137-139`). Scheduling an injection at agent_start would either fire before the first turn exists or have to interrupt a running request; the durable-inbox + idle-claim design gives each reminder its own ordinary turn instead (`.agents/notes/implemented/feature/2026-08-05-durable-web-schedule.md:17`: "Due work waits until the Agent is fully idle, then enters the ordinary next-turn queue through `followup()`; it never steers the current turn").
- **Flooding is bounded.** Fixed-rate reminders skip missed occurrences, present only the latest due occurrence, batch all due records into one message, and enforce a five-minute minimum interval (`domain.ts:514-519,537-538`; `tools.ts:151-152,283-288`; note `:49`; README `:217-218`).

## 3. What the maintainer is seeing: `packages/context/time-context`, not schedule

The block "Time sampled while preparing turn N, step M: \<timestamp\>" is rendered by time-context (`renderText`, `packages/context/time-context/src/index.ts:105`), together with the browser-zone line (`packages/context/time-context/src/request-zone.ts:69-76`) and the elapsed line whose baseline is "model-visible message" at step 1 and "step context" at later steps (`index.ts:102-107`).

Its injection point and cadence:

- Trigger: a **prepended `agent/pre-step` listener** (`index.ts:181-221`), i.e. it runs at every model-request preparation — every step, not every turn. It calls `next()` first, then, if the decision enters the step, appends one user message to `decision.messages` (`index.ts:185-186,211-220`). Unlike schedule's `followup`, this joins the request currently being prepared; the loop then logs it as a durable `user/message` event (`agent.ts:373-377`).
- Message identity: `createUserMessage` with `source: { kind: 'plugin', plugin: 'time-context', form: 'snapshot', sections: [{ name: 'time-context', text }] }` (`index.ts:215-218`) — a plugin-attributed snapshot, distinct from schedule's `{ kind: 'plugin', plugin: 'schedule' }` framing (`runtime.ts:271`).
- Cadence control: `refreshIntervalMs` is the minimum milliseconds between durable injections; omission or `0` injects at **every eligible step** (`index.ts:52-53,189-194`; config table in `packages/context/time-context/README.md`).
- Tests pin the per-request cadence and the reading shape: `tests/time-context.e2e.ts:31` ("uses the process zone and persists one ordered context event per request"), `tests/time-context.spec.ts:158,191`, and `tests/invariant.spec.ts:90` (reading's turn/step/baseline/timestamp must agree with the open turn and pre-step position).
- Why it is present in a schedule session at all: the Schedule overlay mounts both plugins (`apps/cli/config/examples/schedule/cordis.yml:4-8`), documented in `docs/user/guide/schedule.md:7-9` and the note `.agents/notes/implemented/feature/2026-08-05-durable-web-schedule.md:15,41`. Schedule does not depend on time-context (`README.md:72`); time-context exists so the model can interpret unqualified dates in the request-local browser zone before calling `schedule_create`.

## 4. Verdict

There is **no per-turn reminder injection in `packages/schedule/schedule`**. Its only model-visible output is the due-reminder framing delivered as a new turn at a due wall-clock instant, via `followup()` after an idle-phase claim (`runtime.ts:254-273`), plus the durable `schedule/change` dispatch record that makes it auditable (`runtime.ts:280-296`). Everything model-visible is reconstructable from the session log (repo invariant "Model-visible ⟺ logged", `AGENTS.md:111`): the `agent/inbox/spliced` + `user/message` events carry the message, the `schedule/change` dispatch carries the admission. One precision: the package does **not** claim exactly-once in general — a crash between synchronous follow-up admission and the dispatch checkpoint can repeat a reminder (`README.md:219`; note `:59`); "exactly once" holds for the restart-resume case pinned by `jsonl-restart.spec.ts:98`. The per-step "Time sampled" block belongs entirely to `packages/context/time-context` (`index.ts:105,181-221`).
