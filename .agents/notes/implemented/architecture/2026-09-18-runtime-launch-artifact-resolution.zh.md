# Agent Note: runtime launch resolves bare imports on the artifact plane

Status: implemented

[English](2026-09-18-runtime-launch-artifact-resolution.md) | 中文

> Сужает решение [dsh source launch through the tsx ESM hook](2026-07-29-dsh-source-launch-tsx-esm.zh.md): рантайм сохраняет tsx для трансляции source-цепочки входа, но отказывается от проекции tsconfig `paths` для bare-импортов.

## Проблема

Каждая сессия падала на первом вызове инструмента с `Cannot read properties of undefined (reading 'prepare')`. Планировщик agent-loop ищет staged-исполнителя как `ctx.tools[TOOL_RUNTIME_SCHEDULER]`, где ключ — module-level символ из `@deepseek-ai/dsh-tools`. С проекцией базовой карты `paths` на весь процесс этот пакет загружался дважды под двумя модульными идентичностями: импорт строки лоадера конструировал сервис `tools` из `lib/index.js`, а импорт символа в agent-loop связывался с `src/index.ts` через paths-проекцию tsx. Две идентичности — два разных символа, и поиск возвращал `undefined` независимо от того, какая копия «правильная».

Module-level идентичности — символы, реестры, синглтоны — ломаются одинаково; планировщик был лишь первой видимой жертвой. Дуальность идентичностей такого рода — то самое смешение source/artifact, которое решение о source-launch уже отвергло; отличалось только направление (строки утекали на артефактную плоскость вместо входной цепочки).

## Решение

Вектор запуска рантайма закрепляет tsconfig для tsx в [tsconfig.runtime.json](../../../../tsconfig.runtime.json), не содержащем карты `paths`. Скрипты `dsh` и `demo:inspector` задают `TSX_TSCONFIG_PATH`, а `demo:ptc` передаёт ту же переменную окружения в свой запуск. tsx по-прежнему транслирует source-цепочку входа; каждый bare-импорт резолвится через пакетные `exports` — артефактную плоскость — как у опубликованного bin, поэтому весь процесс видит одну модульную идентичность на пакет. Смоук source-launch проверяет вектор скрипта и запускается с той же переменной, а job матрицы Node совместимости собирает артефакты перед ним.

Каждый подпроцессный тестовый харнесс, поднимающий реальный профиль, передаёт в `resolveExampleLaunch` тот же файл — снапшоты записанных сессий, а также e2e- и expected-наборы, — поэтому их потомки в режиме `src` тоже резолвят bare-импорты на артефактной плоскости. Запуск внутри этого смоука сам пропускается, пока собранного вывода нет, и непостроенный coverage-lane остаётся зелёным; агрегаты primary и consumers ставят смоук после своей сборки.

## Рассмотренные альтернативы

**Заставить vendored loader импортировать строки через общую цепочку хуков**, чтобы строки связывались с `src` как весь остальной граф и zero-build сохранялся. Отклонено пока: это перепроектирование vendored порядка резолюции вокруг апстримного взаимодействия (хуки tsx 4.22.4 против fast-path внутреннего импорта лоадера), которое бисектится только полной сборкой плюс живым запуском на каждый шаг. Вернуться, если апстрим починит двойную загрузку напрямую.

**Исключить собранный вывод из базовой карты `paths`.** Отклонено: tsx применяет paths ближайшего tsconfig без учёта `include`, так что язык tsconfig не выражает эту границу.

## Последствия

- `pnpm dsh` на чистом чекауте требует сперва `pnpm run build`: bare-импорты резолвятся в `lib/`, и stale-bundle guard уже требует того же для web-профиля.
- Module-level идентичности снова стабильны во всём рантайме; пакет больше не может загрузиться один раз на каждый путь резолюции.
- Свойство zero-build из июльского решения о source-launch сужено до входной цепочки, которую tsx по-прежнему транслирует из исходников.
